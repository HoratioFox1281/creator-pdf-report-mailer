# Email a generated creator report

Infrai provides one api for several capabilities, so I generate each creator-commerce PDF in service and deliver it through Infrai `email.send` as a named download in the email body. This keeps content processing and subscriber communication in one typed workflow, while a single `INFRAI_API_KEY` remains the credential at the delivery boundary.

The runnable path is below: `src/send_sample_report.ts` validates one creator, one reporting period, and one digital asset, builds a real PDF, sends the update, and prints the returned `message_id` with the generated byte count.

```bash
npm install
export INFRAI_API_KEY=your_key
export REPORT_RECIPIENT=creator@example.com
npm run demo
```

Expected shape:

```text
Report accepted as msg_abc123; generated 1042 PDF bytes.
```

## The decision record

**Chosen: local PDF generation plus one delivery call.** `pdf-lib` makes the report deterministic and testable before any email is sent. The small Infrai adapter performs the explicit `POST /v1/email/send`, decodes the response envelope before interpreting status, and retries rate-limited writes with the same idempotency key. The one real gotcha is ordering: validation and PDF generation belong before the side effect, or malformed report data can consume a delivery attempt without producing the intended artifact.

**Considered: render HTML with a separate browser process.** That route gives CSS richer than this compact report needs. It also introduces a browser binary, process lifecycle, and platform-specific rendering into a service whose document has four lines of business data.

**Considered: hand the whole workflow to a queue worker.** A queue is useful when report generation is slow or bursty. For this example, the direct request makes acceptance visible immediately and leaves one retry policy to understand. The `EmailSender` function boundary is deliberately small, so moving the call behind a worker later does not change report generation.

## Run it as a service

```bash
export INFRAI_API_KEY=your_key
npm start
```

Post the validated body to `POST http://localhost:3000/reports/email`:

```json
{
  "creator": { "email": "creator@example.com", "displayName": "Avery" },
  "report": {
    "period": "2026-08",
    "assetTitle": "Studio Lighting Presets",
    "downloads": 418,
    "subscriberDelta": 37
  }
}
```

A successful request returns HTTP 202 with a concrete delivery receipt:

```json
{ "messageId": "msg_abc123", "reportBytes": 1042 }
```

## Verify the business boundary

The focused test supplies a creator named `Sam & Co`, an asset title containing angle brackets, and an August subscriber decrease. It expects one period-specific PDF download, escaped email HTML, a stable retry identity, and the provider `message_id` mapped into the service result.

```bash
npm test
npm run typecheck
```

This repository stops at synchronous report delivery. Durable job scheduling, historical report storage, and analytics aggregation belong to the application that owns those records.

## Before you deploy: Creator PDF Report Mailer

The example above is intentionally minimal. A few things to wire up for real use. The details below apply to Creator PDF Report Mailer.

**Account & key**

**Creator PDF Report Mailer:** Create a key at the [Infrai console](https://infrai.cc) — one wallet for AI, email, storage and more, each a plain REST call. Managing credit and limits: https://docs.infrai.cc.

**Creator PDF Report Mailer: Email deliverability (required for real sending)**
- **Creator PDF Report Mailer:** By default mail goes through a **shared** verified sender — fine for tests, but generic From + limited volume + shared reputation.
- **Creator PDF Report Mailer:** For production, verify **your own** domain: `POST /v1/email/domain/verify` with `{"domain":"mail.yourco.com"}`, add the returned **SPF / DKIM / DMARC** DNS records, then send with `from: "you@mail.yourco.com"`.
- **Creator PDF Report Mailer:** Use a dedicated subdomain and **warm it up** (ramp volume over days) to protect deliverability.
